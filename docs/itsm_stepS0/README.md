### 4.2 Teacher、用户模拟器与输入边界

- **Teacher（建议，待你决定 D-S0-5）**：`deepseek/deepseek-v4-pro`。
  - 走与 D7 相同的 API 路由，关闭思考（与 D7 的 extra_body 配置相同）；
  - 每题第 1 条轨迹温度 0，第 2 条温度 0.7，两条都生成，用来观察是否存在多种合法完成方式；
  - **风险**：评测的 LLM 文本裁判和 NL 裁判也是 v4-pro（D7）。用它的输出做 SFT，可能让 LLM 裁判的指标偏向 E0-sft 及之后的模型（自偏好）。E1–E5 共用同一份 SFT 权重，彼此比较不受影响；但 E0-base 与 E0-sft 的对比需要以 fuzzy DB 和逐题审读为主，LLM 裁判结果单列。如果改用其他厂商的 Teacher，需要你提供可用的 API 和预算。
- **用户模拟器**：D5 不变，`deepseek/deepseek-v4-flash`，温度 0，持有 persona、known_info 和模拟器指引。
- **Teacher 的输入**：只包括学生可见的内容：
  - Bench2 `policy.md`、94 个工具 schema 加 done、固定问候语；
  - 用户消息、真实工具返回（与 ItsmEnv 的观察字符串相同）。
  - 不提供上游逐题 system prompt，不提供 gold、NL 断言、known_info、task_id、上游 ID 或验证器，也不提供未来观察。
- **执行方式**：Teacher 通过 `ItsmEnv` 操作真实 Bench2 工具，每回合**只能有一个动作**。如果一次返回多个工具调用，或者同时返回文字和工具调用，这一回合作废，带格式提醒重问 1 次（不计 env 步）；再次失败，整条轨迹按格式问题拒绝。所有重试都记录在案。
- **任务解析**：P1/P2/P5 通过 `split_version=itsm_split_v2` 解析。P3/P4（以及 P6）不在 v2 中，S1 需要一个经批准的解析入口：要么先冻结 v3 和用途登记，要么在 S1 中用 `task=` 显式加载批次文件，并在轨迹元数据中记录来源和 sha256。建议前者。
- **不伪造**：工具结果一律来自真实执行；Teacher 不能看到验证器，也不能事后修改轨迹。

### 4.3 每条轨迹的审核（逐条硬性检查 + 全部人工审读）

1. **可执行**：没有 `tool_internal`，以 `agent_done` 结束，没有触发 `response_length` 或 `max_steps` 截断。
2. **身份与权限**：在第一个写操作之前核验操作员身份；手动关闭等操作需要的角色符合 policy。
3. **用户确认**：PROPOSED/ASK 类连带操作先征得用户同意；用户拒绝的不执行（例如 P5 的通知）。
4. **REQUIRED 连带操作齐全**：例如 P5 的 SLA 生成和知识搜索。
5. **没有未授权写入**：把最终 DB 与初始状态做差，写到 gold 范围之外的记录要逐项人工判断。
6. **关键事实**：按 `usage_audit.json` 中 `sft_pilot_candidates[].fact_checks` 检查。P4 逐字核对操作员文本（只规范空白），P5 检查描述里有"冻结、掉线"；P1/P3 不写自由文本。
7. **完成声明**：最后告诉用户的内容与 DB 的实际状态一致。
8. **上游有效验证器**：派生题的验证器全部有效，gold 上全部通过。逐个运行，全部记录。
9. **Bench2 DB（fuzzy）只作诊断**：DB = 0 的轨迹自动进入人工复核，只有写明理由（例如合法的另一种完成方式）才能接纳；DB = 1 本身不算质量证明。

接纳的轨迹**全部由人工审读**：agent 为每条轨迹准备审读表，列出全文和上述检查结果，结论由你（或你指定的审读人）给出，agent 不能自证。被拒绝的轨迹不参与 SFT loss，拒绝原因归入固定类别。

## 5. 学生输入格式、mask 与长度（依赖第 7 步）

- **格式**：一条 SFT 样本是一整条轨迹，token 序列必须与第 7 步验收的 `ItsmAgentLoop` 实际拼出的 ids 完全一致。具体包括：
  - 同一 policy、94 个工具加 done、Qwen3 chat template、`enable_thinking=False`；
  - 观察包装（`OBSERVATION_PROMPT`）、单动作协议、终止规则。
  - 因为 Qwen3 模板重新渲染时会丢掉前面的空 `<think>`（第 6 步已确认），**不能**对整段对话重新调用 `apply_chat_template`，必须按 loop 的增量方式拼接。
- **verl 现有入口**：`verl/utils/dataset/multiturn_sft_dataset.py` 对每条消息单独渲染，assistant 消息 mask=1，并去掉 generation prompt。它的 ids 是否等于 loop 的 ids，要在 S2/S3 逐 token 比对，**只能作为候选入口**，不能直接宣称兼容。
- **监督范围**：
  - **loss = 1**：每个审定动作的生成部分，即动作文本（工具调用 JSON、消息文本或 done）加上结束符 `<|im_end|>`；
  - **loss = 0**：system（policy 与工具 schema）、固定问候语、用户和模拟器的回合、工具观察、generation prompt（`<|im_start|>assistant\n<think>\n\n</think>\n\n`）、换行分隔、padding。
  - 被接纳轨迹中的错误调用，以及之后的恢复动作是否监督：试点阶段错误动作 mask = 0，只作上下文；是否保留这类轨迹，S1 之后再定。
- **对齐检查**（S2/S3 执行）：
  - 把每段监督 token 解码，应与预期的动作渲染逐字相同；
  - 监督段的第一个 token 紧跟在 generation prompt 之后，`<|im_end|>` 包含在监督段内；
  - 工具 JSON 能被第 7 步的动作解析器解析，并还原为同一个 `ItsmAction`；
  - label shift 由训练器统一处理，要检查第一个和最后一个监督位置。
- **监督 token 很少**：脚本化 gold 回放中，生成 token 只占完整序列的约 0.3%–2%（train 题为 90–664 / 28.6k–33.9k；6D-2 四题为 283–903）。所以 loss 归一化方式（建议按整批监督 token 平均）和每条样本的计算量（主要花在 28k 的 prompt 前缀上）都需要在 S3 固定。
- **长度**：
  - 完整观察，不裁剪，不轮换上下文；
  - 超过 40,960，或被 `response_length` 截断的轨迹，不作为 SFT 样本（拒绝并记录）；
  - "当前可见历史 → 下一动作"的切分格式本步不提议；
  - **40,960 仍是待验证的候选值**，SFT 不改变这一点。
- **显存验证**：第 7 步验证推理在 32,768 和 40,960 下的长度与显存；S3 按实际最长的接纳轨迹验证训练显存（LoRA 和全参数分别测，见 §6）。

## 7. 实验设计与协议差异

- **实验**：
  - E0-base：未做 SFT 的 Qwen3-8B；
  - E0-sft：S4 冻结的 SFT 权重，记录完整哈希；
  - E1–E5：都从这**同一份** SFT 权重独立起跑，每个实验重新初始化 RL 优化器和调度器，不继承前一个实验的 RL 权重；
  - 纯 GRPO 对照本轮不启动，如需要另行审批。
- **SFT 的固定预算与 checkpoint 规则**：S2/S3 冻结 epoch、步数、学习率和监督 token 数；取预先规定的最终步作为 checkpoint，中间的 checkpoint 只作诊断，不用 dev 或 held-out 挑选。
- **RL 的固定预算与 checkpoint 规则**：第 8 步预先确定步数、episode 数、有效组口径和成本上限；checkpoint 取预先规定的步，不用 dev 或 held-out 挑选。AirlineRL 的 75 步不能照搬。
- **KL reference**：如果启用 KL，reference 就是那份共同的 SFT 初始化权重，E1–E5 相同，在云端核对实际加载的权重和哈希，不能悄悄指向原始 base。behavior / old policy 是每批实际采样时的策略版本，与 reference 是不同的角色。SFT 的优化器状态不带入 GRPO。
- **诊断协议**：
  - 第 8 步：在 GRPO 池（32 题）上做 E0-base 的 train 诊断，在 dev（13 题）上测开发基线，两者分开报告；
  - S5：用同一协议测 E0-sft，包括逐题成功次数、pass@k、实际 G 组的混合率和组内 reward 方差；
  - held-out 不参与试点、调参或长度测量。
- **与原路线的差异**：

| 项 | 原路线（playbook v1） | 新路线（playbook2） |
|---|---|---|
| 训练方式 | 纯 GRPO 首选，SFT 不在授权范围（6D-1 决定） | SFT → GRPO；纯 GRPO 只作以后另批的对照 |
| 训练题用途 | 一个"通过/隔离"标签 | GRPO 和 SFT 分开准入：both / SFT-only / GRPO-only / dev / held-out / quarantined |
| GRPO 池 | v3 预期 train 36 | 建议 32（4 道派生题因 R1 暂停 GRPO，划分不变） |
| 隔离对象 | GRPO train 对照 dev/held-out | SFT∪GRPO 对照 dev/held-out |
| 第 7 步之后的顺序 | 7 → 8 → 9 … | S0 → 7 → 8 → S1 → … → S5 → 9 …（每一步单独批准） |
| 不变的部分 | — | D1–D8、fuzzy 阈值、policy、gold、v1/v2、预算 v1 的数值、完整观察规则、40,960 仍待验证 |
