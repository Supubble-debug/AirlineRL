# Bench2 → AirLineRL：云端实施评估与逐步 Agent 提示词

日期：2026-10-27。

依据：用户提供的《Bench2迁移AirLineRL强化学习方案.md》，以及本地 AirLineRL / Bench2 源码静态检查。实施和训练位置为用户指定的云端 SSH 环境。本地机器配置不作为训练能力判断依据。

当前仅完成方案评估、源码核对和本提示词文档。尚未连接云端、安装依赖、修改训练代码、运行测试或训练。云端版本与本地是否一致，需要第 0 步验证。

## 一、可行性结论

工程上有条件可行。保留 Bench2 的 ITSM 业务环境、用户模拟和评分器，新增 ITSM adapter、rollout loop、数据入口与训练入口，复用 AirLineRL 的训练算法，是合理路线。不能仅把 airline 配置改为 itsm。

工程链路跑通与算法效果提升是两个验收目标：前者可以通过接口测试和真实训练 smoke 验证；后者需要冻结数据划分、基线、消融和独立评测，不能提前保证。

本地源码已核实：

- `src/agent_rl/trainer/preflight.py` 与 `verl_entry.py` 锁定 airline 协议，需新增 ITSM 路径，保持原 airline 校验有效。
- `Bench2/src/enterprise_worlds/gym/gym_agent.py` 固定生成 `gym_call`；默认跳过 NL 断言；step 的 truncated 固定为 False；后台执行路径未设置任务时钟。
- Gym 的 close/reset 仅有限等待线程，不能据此证明旧 episode 已退出；必须验收取消、超时和资源回收。
- `TauAgentLoop._finalize_episode()` 依赖 tau 的 simulation_run，ITSM 需要真实结构化轨迹导出。
- 现有 rollout 在缺少采样 logprob 时填零。ITSM 训练必须验证真实采样 logprob 的来源，或明确验证训练器如何在正确策略版本下重算所需概率；不能把零值伪装成真实采样记录。
- 上下文轮换会清空此前 response token、mask、logprob 和 turn span。迁移时要明确采用末段训练还是完整分段训练，并记录保留比例，不能声称自动覆盖完整轨迹。
- 本地 tasks.json 共 53 题：31 MSP、22 single；全部包含 gold actions 和 NL assertions。它足以作为工程试点，但任务数量少、存在相似工作流，泛化结论需要谨慎。

## 二、需要补充到原方案的约束

1. 云端运行环境独立验收。核对实际 Python、CUDA、PyTorch、vLLM、verl、Bench2 和 tau2 版本及 GPU；仓库声明 Python 3.12，不能据此假定云端已具备兼容环境。
2. 先确定 episode 协议，再接训练器。任务时间、工具 ID、增量观察、终止原因、错误分类和轨迹导出必须可测试。
3. DB 自由文本比较策略显式配置并记录 effective strategy，防止 llm 静默退回 fuzzy。未计算 NL 时，NL/联合分数记录为未评估，不能当作通过。
4. 同组 G=4 必须对应同一题目、同一策略版本、独立数据库。基础设施失败不能伪装成模型失败参与训练；重试、丢弃或整组重采样策略需要固定，避免凑组或跨版本混组。
5. split 在模型效果调试前冻结，按工作流家族分组，检查跨 tenancy 的近重复。开发阶段仅用 train/dev；held-out 不用于调参、选预算或挑 checkpoint。
6. E1/E2/E3/E4/E5 均从同一基座独立初始化。“按顺序实施”不表示后一个实验继承前一个训练权重。
7. 奖励编码的总和守恒不仅检查函数本身，还要检查经过 verl worker 后处理、mask、padding、dtype 及实际奖励处理路径后是否仍成立；若启用 KL 奖励项，需明确它与证据解码的交互。
8. GRPO 同组全 0 或全 1 时组内 outcome 优势为 0。真实训练验收必须观察有效组比例和真实参数更新，不能只看进程跑完。
9. 评估同时报告 DB、NL、联合成功率、失败类型、截断、成本和有效组比例。多次评测 seed 不等于增加独立任务数；按任务汇总不确定性，避免夸大统计证据。
10. 迁移本身不自动构成算法创新。论文结论应区分 ITSM 适配工程、算法消融和跨域有效性证据。

## 三、给云端 AI agent 的总提示词

将以下提示词发给已连接云端 SSH 工作区的 agent。原方案及本文件需能在云端读取，或直接将内容提供给 agent；本地 D 盘路径不是云端路径。

```text
你是本项目的实现工程师。目标是在现有 AirLineRL 仓库中接入 Bench2 ITSM，
逐步完成环境适配、冻结基线、E1/E2/E3/E4/E5 和独立评测。

执行环境：用户指定的云端 SSH 工作区。所有安装、测试、模型采样和训练均在云端进行。
不要在本地安装训练依赖或启动训练。不要猜测 SSH 主机或云端项目路径。
若当前会话尚未连接云端，先告知缺少的连接/工作区信息，停止执行。

先读取云端仓库适用的 AGENTS.md、用户提供的迁移方案，以及
docs/itsm_migration_agent_playbook.md（若不存在则使用我在对话中提供的内容）。
方案中的新增接口是设计，不代表当前代码已经实现。所有状态以云端源码和实际输出为准。

【最高优先级的执行规则】
1. 本次仅获准执行第 0 步。不得自行进入第 1 步。
2. 每次最多执行一个编号步骤；该步内部可以完成必要的实现、测试与修复。
3. 完成本步后必须结束本轮，等待我验收。
4. 只有我明确说“第 N 步验收通过，执行第 N+1 步”，才进入下一步。
   我的提问、日志补充、要求修改或“测试通过”本身，都不等于授权下一步。
5. 如果我要求修正，只修正当前步骤并重新提交验收；不得顺带做后续步骤。
6. 不创建自动继续任务，不后台启动下一阶段，不擅自进行整套迁移。
7. 遇到跨步骤阻塞时说明阻塞和最小解决方案，等待我决定是否调整当前范围。

【实现约束】
- 保留 airline 原有实验协议。优先新增 ITSM 模块，不把 airline 的校验简单放宽。
- 复用 Bench2 的真实业务工具、数据库、用户模拟器和评分器。
- gold actions、NL assertions、完整 known_info 等私有字段不得被直接注入策略输入。
  策略只能看到公开政策、工具 schema、用户在对话中提供的信息及真实工具观察。
- gold 仅可用于评分和明确标注的离线环境测试；不能把 gold 回放当作模型能力。
- 所有 episode 独立数据库；任务时钟在实际执行及评分线程一致，并可靠清理。
- 保留真实工具调用、唯一 ID、结构化错误、结果是否收到和终止原因。
- 生成 token 的 loss mask 为 1；用户/工具/环境观察及固定问候等非策略采样 token 为 0。
- 不伪造采样 token 或 logprob；明确上下文截断/轮换后的训练范围。
- 基础设施错误与模型行为错误分开处理，不能静默转成训练 reward=0。
- 训练和调试不读取 held-out 成绩来调参。每个实验从相同基座独立初始化。
- 不覆盖用户已有修改，不读取或输出密钥，不更换系统环境来绕过依赖问题。
  环境准备步骤使用独立环境；后续步骤缺依赖时先报告，不擅自全局升级。
- 不修改奖励或测试期望来制造通过。未执行、mock、离线回放、真实模型测试须分开标注。

【每一步的交付格式】
1. 当前步骤、目标、状态：待验收 / 阻塞 / 修订待验收。
2. 本步改动文件及改动目的；只读步骤写“无代码改动”。
3. 实际运行命令、工作目录、退出码、关键结果和日志路径。
4. 验收条目：逐项说明通过、失败或未执行；不能用计划替代结果。
5. 我可以复查的命令、产物和预计可见结果。
6. 风险、未验证事项及下一步建议范围。
7. 最后一行固定为：“第 N 步待你验收；收到明确通过指令前，不执行第 N+1 步。”

实施后将进度保存在 docs/itsm_migration_progress.md：
记录已批准步骤、当前待验收步骤、运行环境/版本、改动、验证证据和阻塞。
第 0 步为只读审计，暂不创建进度文件。后续首次获准写文件时再建立。
“测试已通过”与“用户已批准”必须分开记录，不得自行填写用户批准。

现在只执行第 0 步，完成后停止。
```

## 四、步骤卡：一次只批准一行

步骤编号表示工程推进顺序，不表示实验权重继承顺序。每步运行规模在开始时声明；正式长训练的预算由前一步产物确定并经用户验收。

| 步骤 | 允许工作与交付 | 验收标准与停止点 |
|---|---|---|
| 0：云端只读审计 | 确认工作目录、仓库/子模块版本、工作区改动、Bench2 来源及数据校验值；核对接口、GPU/显存、Python/CUDA/依赖与现有测试入口；输出差异与后续文件计划。不安装、不改代码、不调用付费模型。 | 明确可复用模块、阻塞项、独立环境方案、云端与本地方案差异。审计结束即停。 |
| 1：独立环境与现有测试基线 | 按已批准方案建立或复用云端独立环境，保存实际依赖版本。运行与迁移有关的现有离线测试；记录既有失败，不扩展修复范围。 | 核心依赖可导入，测试命令可复现，既有失败有清单；不运行模型或训练。建立进度文件后停。 |
| 2：接口与奖励契约 | 仅编写 ITSM 协议文档：reset/step/close、公开/私有字段、增量观察、调用 ID、终止原因、时钟、错误分类、数据库隔离、reward、token 保留与组失败策略。 | 给出正常工具调用、工具报错、done、超时、截断各自的数据样例及预期行为。不实现 adapter，提交设计后停。 |
| 3：离线环境与评分回归 | 使用真实工具对全部任务 gold 回放，显式固定 task 时间与文本比较策略；增加原方案 MSP-021、Single-017 的关键正反例。 | 正例 DB=1；预定错误反例 DB=0；重复回放一致。证明环境与评分一致性，不声称模型成功。完成后停。 |
| 4：最小单 episode adapter | 实现 itsm_env 与 schema/动作转换，唯一调用 ID、增量观察、结构化轨迹和真实工具结果；用脚本代理/确定性用户替身验收。 | 正常、错误、恢复、done 均可复查；调用和返回一一对应；无整段历史重复追加；不接训练器。完成后停。 |
| 5：生命周期与隔离 | 实现任务时间清理、重复 reset/close、用户早停、步数/token 截断、基础设施异常、取消与超时；验证并行独立数据库。 | 旧 episode 退出后才可重置，无残留工作修改新状态；时钟及数据库无串扰；退出原因可区分。线程无法可靠终止时采用可回收的进程隔离等明确方案。完成后停。 |
| 6：数据划分与预算冻结 | 建立 task family / tenancy / 业务类型清单及固定 train/dev/held-out manifest；检查近重复。测量 schema、政策和长参数 token 开销，制定训练与评测预算、seed、文本比较和模拟器配置。 | split 不重叠且相似家族不泄漏；模型输入不含答案字段；预算有测量依据；不通过 held-out 模型表现选预算。完成后停。 |
| 7：冻结策略 loop 与 token 验证 | 接入云端当前策略采样服务，实现 ItsmAgentLoop；先确定性采样替身验证，再在少量 train/dev 任务上进行有限真实采样；不更新权重。 | token、logprob、mask、turn span 长度和来源可核验；环境 token mask=0；无私有字段泄漏；上下文策略与 token 保留比例明确。模拟数据不能代替真实采样验收。完成后停。 |
| 8：E0 开发基线 | 用冻结模型和固定 harness 在 dev 运行有界基线，保存完整轨迹、DB/NL 分项、截断、成本与工具错误。 | 结果可复查，异常单列；不把未做 NL 的 DB-only 结果称联合成功率。冻结正式实验协议和选 checkpoint 规则，held-out 保留到最终评测。完成后停。 |
| 9：ITSM 训练入口与 E1 smoke | 实现独立数据构建、入口与 preflight；dry-run 后运行 1–2 个真实优化步、少量训练题、G=4。验证保存和重新加载；有条件时做一次短恢复检查。 | 同组题目/策略版本一致、数据库独立；奖励与分组正确；loss/梯度有限；至少有效组产生可观测参数更新。若全部零优势，停止并提交诊断，不靠伪造奖励通过。输出正式 E1 预算后停。 |
| 10：E1 正式训练 | 从基座独立启动 outcome-only sequence GRPO，严格使用已批准的步数、采样及资源预算。保存配置、版本、日志和 checkpoint。 | 实际优化步数与预算一致；报告有效组比例、失败/重试、奖励和资源消耗；按预定规则选 checkpoint，不查 held-out 调参。完成后停。 |
| 11：E2 | 从相同基座独立训练，只改变 balanced 聚合；先做必要短验证，再执行批准的同等预算。 | 配置差异可审计，分组和奖励协议与 E1 一致；不要求结果必须高于 E1。完成后停。 |
| 12：E3 | 先验证真实工具失败、缺失结果、恢复、截断如何映射过程证据，再进行 sequence + process 独立实验。 | 正负证据对齐正确回合；权重显式固定；工具成功不等于业务成功；不使用 gold 序列相似度 shaping。完成后停。 |
| 13：E4 | 验证 hindsight 及奖励编码经过真实 verl 路径的守恒与 mask 对齐，再从基座独立运行 sequence + hindsight。 | 标量 reward 保持 outcome-only；证据不污染观察 token；数值误差有明确容限；上下文丢弃回合不被错误广播。完成后停。 |
| 14：E5 | 在独立组件验收后组合 balanced + light process + hindsight，从相同基座独立训练。 | 对照 E2/E3/E4 的差异明确，奖励和证据来源一致；不根据结果临时改变协议。完成后停。 |
| 15：冻结 held-out 评测 | 一次性按冻结规则评测 E0–E5，统一 harness、任务、评测 seed、模拟器、裁判、文本比较与预算；报告分项及误差分析。 | 展示任务级汇总、运行失败、成本和统计局限；不得将不同 seed 当作独立新任务，不用结果返回修改当前实验。结果报告提交后停。 |

## 五、后续每轮可以直接发的短提示词

批准下一步：

```text
第 N 步验收通过。现在仅执行第 N+1 步，按总提示词和对应步骤卡提交产物及验证证据。
完成后停止，等待我验收。此授权不包含第 N+2 步。
```

要求修改当前步骤：

```text
第 N 步暂不通过。只修正以下问题：[列出问题]。
重跑受影响的验证，更新证据并重新提交第 N 步验收；不要进入第 N+1 步。
```

换会话后恢复：

```text
先读取项目的总提示词和 docs/itsm_migration_progress.md。
最近一次由我明确批准的步骤是第 N 步；当前仅允许执行/修订第 M 步。
不要将上一个 agent 的“完成”或“测试通过”视作我的批准。
检查当前云端版本和未提交修改后，仅继续第 M 步，完成后等待验收。
```

如单步仍太大，用户可在批准前把它拆成子步骤（例如 9a dry-run、9b 一步更新、9c 恢复检查），每个子步骤单独验收。Agent 不得把这样的拆分当作自动批准全部子步骤。
